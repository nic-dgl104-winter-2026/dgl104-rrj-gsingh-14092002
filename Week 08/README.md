### Activity 1: Research a New Programming Language – Processing
 
For this activity, I researched **Processing**, a programming language I had not worked with before.
 
**What is Processing used for?**  
Processing is a flexible software sketchbook and language designed for **visual arts and creative coding**. It is primarily used to create visual, interactive, and animated programs. Artists, designers, and educators use it to produce generative art, data visualizations, and interactive installations. It runs on top of Java, making it accessible while still being powerful.
 
**Who uses Processing?**  
Processing is used by visual artists, graphic designers, educators, and creative coders. It is widely used in university art and design programs, and has a large community of creators who share their sketches and projects online through the official Processing website and platforms like OpenProcessing.
 
**Useful Resources:**
 
| Resource | Why It Is Useful |
|---|---|
| [processing.org](https://processing.org) | Official site with documentation, tutorials, and examples |
| [OpenProcessing](https://openprocessing.org) | Community platform with thousands of real sketches to learn from |
| [The Coding Train (YouTube)](https://www.youtube.com/c/TheCodingTrain) | Beginner-friendly video tutorials by Daniel Shiffman, a well-known Processing educator |
 
**Reflection:**  
Researching Processing was genuinely eye-opening. Before this activity, I had never thought about programming being used as a tool for art and visual design. Learning that Processing was built specifically for creative coders — not for building apps or websites — changed how I think about what programming languages can do. Reading other students' Mattermost posts about Haskell and Lua reinforced this idea. Haskell is a purely functional language used in academia, while Lua is a lightweight scripting language embedded in games. Each language reflects the specific problem it was designed to solve. This made me appreciate that choosing the right language for a project matters more than simply picking the most popular one.

### Activity 2: Write a User Story
 
For this activity, I chose **Spotify** and focused on the **playlist creation feature**.
 
**General User Story:**  
*"As a user, I can create a new playlist to organize my favourite songs."*
 
**More Specific User Stories:**
 
- *"As a user, I can create a playlist and give it a custom name so that I can find it easily later."*
- *"As a user, I can add songs to a playlist directly from the search results so that I don't have to navigate away from what I'm doing."*
- *"As a user, I can reorder songs within a playlist so that I can control the listening experience."*
- *"As a user with a free account, I want to know if any playlist features are restricted so that I understand what I have access to."*
 
**Acceptance Criteria for:** *"As a user, I can create a playlist and give it a custom name"*
 
- [ ] A clearly visible **"Create Playlist"** button is accessible from the main sidebar or library.
- [ ] The user is immediately prompted to enter a name upon playlist creation.
- [ ] The playlist name field accepts at least 100 characters.
- [ ] The newly created playlist appears immediately in the user's library without a page refresh.
- [ ] If no name is entered, a default name (e.g., *"My Playlist #1"*) is automatically assigned.
 
**Reflection:**  
Writing user stories felt simple at first, but the challenge appeared when I tried to get more specific. The general story — *"I can create a playlist"* — does not tell a developer much. More specific stories, especially the one about free account restrictions, showed how different types of users interact with the same feature in very different ways. Writing acceptance criteria forced me to think like both a user and a developer at the same time. I now understand why functional requirements matter: without them, developers make assumptions, and those assumptions often do not match what users actually need (DGL 104 Course Notes, Week 8, 2025).
